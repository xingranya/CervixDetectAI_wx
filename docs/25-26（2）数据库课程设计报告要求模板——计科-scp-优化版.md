# 1 需求分析

## 1.1 研究意义

随着微信小程序成为个人健康管理服务的重要入口，用户在完成线下健康检查后，往往需要长期保存检查摘要、按时间管理复查提醒，并在就诊前整理需要向专业人员确认的问题。**云端智诊女性健康管理小程序**（项目代号 `cervixdetectai_wx`）围绕"记录、提醒、整理、了解、反馈"五类需求展开，定位为健康信息管理工具，**不提供**在线诊断、治疗方案、处方或问诊服务。

本系统采用**微信原生小程序**作为前端，**Express 4** 作为轻量 API 服务，**MySQL** 作为核心数据存储。数据库设计的重点是：

1. 用 `wx_users` 与 `wx_sessions` 表支撑微信登录态；
2. 用 `wx_health_records`、`wx_reminders`、`wx_user_questions` 表形成用户健康管理闭环；
3. 用 `wx_articles` 与 `wx_feedback` 表支持内容浏览与意见收集；
4. 通过外键、组合索引、视图、存储过程和触发器提高数据一致性与查询效率；
5. 通过 `ON DELETE CASCADE` 保证用户注销时业务数据同步清理。

## 1.3 系统功能

| 模块 | 关键能力 | 后端接口 |
|------|----------|----------|
| 登录与用户资料 | 小程序端 `wx.login()` 获取 `code`，后端 `code2Session` 换 `OpenID` 并生成 64 位 hex `token`；支持昵称、头像（base64 上传）维护 | `POST /auth/login` · `GET /me` · `PUT /me/profile` · `POST /me/avatar` |
| 首页概览 | 展示最近一次检查摘要、下一次复查提醒、记录数与待关注项；`/home` 摘要 + 指标数组 | `GET /home` |
| 检查记录 | 新增、查看、编辑、删除健康检查摘要；状态枚举：`已记录 / 待复查 / 待关注 / 已完成` | `GET/POST/PUT/DELETE /records[/:id]` |
| 复查提醒 | 增删改、标记完成；可选微信订阅消息（按需开启） | `GET/POST/PUT/DELETE /reminders[/:id]` · `PATCH /reminders/:id/done` |
| 问题整理 | 模板多选 + 自定义问题，咨询后补充 `answer_text`；批量保存上限 20 条 | `GET /questions` · `POST /questions` · `POST /questions/batch` · `PUT/DELETE /questions/:id` |
| 健康知识 | 按 `is_active` 和 `sort_order` 展示知识卡片与正文弹层 | `GET /articles` |
| 意见反馈 | 类型枚举 `功能建议 / 使用问题 / 隐私与数据 / 其他反馈`，后端做合规词拦截 | `POST /feedback` |

**接口基础路径**：`/api/miniapp`，鉴权方式：`Authorization: Bearer <token>`，除 `POST /auth/login`、`GET /question-templates`、`GET /articles` 外均需登录。

**关系说明**：

- `wx_users` 与 `wx_sessions`、`wx_health_records`、`wx_reminders`、`wx_user_questions`、`wx_feedback` 均为 1:N 关系，通过 `user_id` 外键关联，`ON DELETE CASCADE`。
- `wx_question_templates` 与 `wx_user_questions` 在业务上表现为"模板转存为用户问题"，当前数据库直接保存转存后的问题文本；如需追溯模板来源，可后续追加 `template_id` 外键。
- `wx_articles` 是全用户共享的健康知识表，无 `user_id`，由运营方统一维护。

# 3 数据库逻辑结构设计

E-R 图向关系模型转换后，得到 8 张表的关系模式（主键加粗，外键标 `FK`）：

**小程序用户表** `wx_users`(<u>**id**</u>, openid, nickname, avatar_url, phone, gender, created_at, updated_at)

**小程序登录会话** `wx_sessions`(<u>**token**</u>, <u>user_id</u> FK→wx_users, expires_at, created_at)

**健康检查摘要记录** `wx_health_records`(<u>**id**</u>, <u>user_id</u> FK→wx_users, record_date, title, project, summary, suggestion, status, created_at, updated_at)

**复查提醒** `wx_reminders`(<u>**id**</u>, <u>user_id</u> FK→wx_users, title, remind_date, description, done, completed_at, created_at, updated_at)

**就诊前问题模板** `wx_question_templates`(<u>**id**</u>, content, sort_order, is_active, created_at, updated_at)

**用户整理的问题清单** `wx_user_questions`(<u>**id**</u>, <u>user_id</u> FK→wx_users, question_text, answer_text, created_at, updated_at)

**健康管理知识** `wx_articles`(<u>**id**</u>, title, summary, content, sort_order, is_active, created_at, updated_at)

**用户反馈** `wx_feedback`(<u>**id**</u>, <u>user_id</u> FK→wx_users, feedback_type, contact, content, created_at)

### 3.1 数据完整性约束

| 约束类型 | 实现位置 | 示例 |
|----------|----------|------|
| 实体完整性 | 主键约束（PK） | `wx_users.id` 自增；`wx_health_records.id` / `wx_reminders.id` 为 32 字符紧凑 UUID；`wx_feedback.id` 为 36 字符标准 UUID |
| 参照完整性 | 外键约束（FK）+ `ON DELETE CASCADE` | 5 张业务表 → `wx_users.id`；会话表按 `user_id` 关联用户 |
| 用户唯一性 | 唯一索引 `uk_wx_users_openid` | 同一微信 OpenID 多次登录不会重复创建用户 |
| 域完整性 | 字段类型、长度、`NOT NULL`、默认值 | `status` 默认 `已记录`；`done` 默认 `0`；`is_active` 默认 `1` |
| 用户定义完整性 | 触发器 + 服务层 | `trg_feedback_before_insert` 拦截空内容；服务层 `assertComplianceText` 拦截合规词 |

### 3.2 范式分析

- 所有表均满足 **第三范式（3NF）**：每个非主属性既不部分依赖也不传递依赖于主键。
- 没有刻意反范式化，但 `wx_articles.content` 与 `wx_health_records.summary` 为业务常用长文本字段，保持在同一表内避免 JOIN。
- 后续若引入搜索能力，可为 `wx_articles.content` 单独建立全文索引（MySQL 8.0+ `FULLTEXT`），不破坏范式。

# 4 数据库物理结构设计

```text
│ PK id        │        │ PK token     │        │ ──────────────────── │
│ UK openid    │        │ FK user_id   │        │ PK id                │
│ nickname     │        │ expires_at   │        │ content              │

       │ 1
       │
       │ * ┌──────────────────────┐ ┌──────────────────────┐ ┌──────────────────────┐
       ├───│  wx_health_records   │ │   wx_reminders       │ │ wx_user_questions    │
       │   │ ──────────────────── │ │ ──────────────────── │ │ ──────────────────── │
       │   │ PK id (UUID32)       │ │ PK id (UUID32)       │ │ PK id                │
       │   │ FK user_id           │ │ FK user_id           │ │ FK user_id           │
       │   │ record_date,status   │ │ remind_date,done     │ │ question_text,answer │
```

## 4.2 建库建表语句

```sql
-- 4.2.1 创建数据库
CREATE DATABASE IF NOT EXISTS cervixdetectai_wx
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

USE cervixdetectai_wx;

-- 4.2.2 小程序用户表
CREATE TABLE IF NOT EXISTS wx_users (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户编号',
  openid      VARCHAR(128)    NULL                COMMENT '微信 OpenID',
  nickname    VARCHAR(80)     NOT NULL DEFAULT '微信用户' COMMENT '昵称',
  avatar_url  VARCHAR(500)    NULL                COMMENT '头像外链',
  phone       VARCHAR(32)     NULL                COMMENT '手机号（保留）',
  gender      VARCHAR(16)     NULL                COMMENT '性别（保留）',
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP
                                          ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_wx_users_openid (openid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='小程序用户表';

-- 4.2.3 登录会话表
CREATE TABLE IF NOT EXISTS wx_sessions (
  token       CHAR(64)        NOT NULL COMMENT '登录令牌',
  user_id     BIGINT UNSIGNED NOT NULL,
  expires_at  DATETIME        NOT NULL,
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (token),
  KEY idx_wx_sessions_user_expires (user_id, expires_at),
  CONSTRAINT fk_wx_sessions_user
    FOREIGN KEY (user_id) REFERENCES wx_users (id)
    ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='小程序登录会话';
```

# 5 数据库的实施

## 5.1 数据库索引设计

| 表名 | 索引名 | 索引字段 | 索引类型 | 设计目的 |
|------|--------|----------|----------|----------|
| `wx_users` | `PRIMARY` | `id` | 主键索引 | 按用户编号定位资料 |
| `wx_users` | `uk_wx_users_openid` | `openid` | 唯一索引 | 保证微信用户唯一 |
| `wx_sessions` | `PRIMARY` | `token` | 主键索引 | 按登录令牌校验会话 |
| `wx_sessions` | `idx_wx_sessions_user_expires` | `user_id`, `expires_at` | 普通索引 | 快速清理或查询用户会话 |
| `wx_health_records` | `PRIMARY` | `id` | 主键索引 | 按记录号定位 |
| `wx_health_records` | `idx_wx_health_records_user_date` | `user_id`, `record_date` | 普通索引 | 按用户和检查日期倒序查询记录 |
| `wx_reminders` | `PRIMARY` | `id` | 主键索引 | 按提醒号定位 |
| `wx_reminders` | `idx_wx_reminders_user_done_date` | `user_id`, `done`, `remind_date` | 普通索引 | 首页和提醒页快速查待办提醒 |
| `wx_question_templates` | `PRIMARY` | `id` | 主键索引 | 按模板号定位 |
| `wx_question_templates` | `idx_wx_question_templates_active_sort` | `is_active`, `sort_order` | 普通索引 | 只展示启用模板并按顺序返回 |
| `wx_user_questions` | `PRIMARY` | `id` | 主键索引 | 按问题号定位 |
| `wx_user_questions` | `idx_wx_user_questions_user_time` | `user_id`, `updated_at`, `created_at` | 普通索引 | 按用户查看最近更新的问题 |
| `wx_articles` | `PRIMARY` | `id` | 主键索引 | 按文章号定位 |
| `wx_articles` | `idx_wx_articles_active_sort` | `is_active`, `sort_order` | 普通索引 | 只展示启用文章并按顺序返回 |
| `wx_feedback` | `PRIMARY` | `id` | 主键索引 | 按反馈号定位 |
| `wx_feedback` | `idx_wx_feedback_user_time` | `user_id`, `created_at` | 普通索引 | 按用户和时间追踪反馈 |

**索引设计原则**：

- **主键索引**：每张表必备，用于按 ID 精确定位。
- **唯一索引**：仅 `openid` 字段需要，强制约束一个微信号只对应一个用户。
- **组合索引**：按真实查询路径设计，把"用户归属过滤"放在最前，再叠加"时间倒序"或"状态过滤"。

## 5.2 数据库视图设计

### 5.2.1 用户健康概览视图

```sql
CREATE OR REPLACE VIEW v_user_health_overview AS
SELECT
  u.id                                        AS user_id,
  u.nickname,
  COUNT(DISTINCT r.id)                        AS record_count,
  MAX(r.record_date)                          AS latest_record_date,
  SUM(CASE WHEN m.done = 0 THEN 1 ELSE 0 END) AS pending_reminder_count,
  MIN(CASE WHEN m.done = 0 THEN m.remind_date ELSE NULL END) AS next_remind_date
FROM wx_users u
LEFT JOIN wx_health_records r ON r.user_id = u.id
LEFT JOIN wx_reminders       m ON m.user_id = u.id
GROUP BY u.id, u.nickname;
```

**用途**：为 `/home` 接口提供用户记录数、最近记录日期、待办提醒数和下一次提醒日期。

### 5.2.2 待办提醒视图

```sql
CREATE OR REPLACE VIEW v_pending_reminders AS
SELECT
  m.id, m.user_id, u.nickname, m.title, m.remind_date, m.description
FROM wx_reminders m
JOIN wx_users u ON u.id = m.user_id
WHERE m.done = 0
ORDER BY m.remind_date ASC, m.created_at DESC;
```

**用途**：集中查询未完成提醒，便于提醒页和管理后台快速检索。

## 5.3 数据库存储过程设计

### 5.3.1 新增健康检查记录

```sql
DELIMITER $$

CREATE PROCEDURE p_create_health_record(
  IN p_user_id    BIGINT UNSIGNED,
  IN p_record_date DATE,
  IN p_title      VARCHAR(120),
  IN p_project    VARCHAR(120),
  IN p_summary    VARCHAR(500),
  IN p_suggestion VARCHAR(500),
  IN p_status     VARCHAR(40)
)
BEGIN
  DECLARE v_id VARCHAR(32);
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK;
    RESIGNAL;
  END;

  START TRANSACTION;
  SET v_id = REPLACE(UUID(), '-', '');

  INSERT INTO wx_health_records
    (id, user_id, record_date, title, project, summary, suggestion, status)
  VALUES
    (v_id, p_user_id, p_record_date, p_title, p_project, p_summary,
     p_suggestion, COALESCE(NULLIF(p_status, ''), '已记录'));

  COMMIT;
  SELECT * FROM wx_health_records WHERE id = v_id;
END $$

DELIMITER ;
```

**说明**：使用事务保证主键生成与插入的原子性，并为后续多表写入预留扩展点；`COALESCE + NULLIF` 把"空字符串"和"NULL"统一规整为默认状态。

### 5.3.2 标记提醒完成

```sql
DELIMITER $$

CREATE PROCEDURE p_complete_reminder(
  IN p_user_id     BIGINT UNSIGNED,
  IN p_reminder_id VARCHAR(32)
)
BEGIN
  UPDATE wx_reminders
  SET done = 1, completed_at = NOW(), updated_at = NOW()
  WHERE id = p_reminder_id AND user_id = p_user_id;

  SELECT * FROM wx_reminders
  WHERE id = p_reminder_id AND user_id = p_user_id;
END $$

DELIMITER ;
```

**说明**：封装"标记完成"的状态变更与时间戳写入，避免前端代码或后端 ORM 重复书写；通过 `user_id` 限定归属，防止越权。

## 5.4 数据库触发器设计

### 5.4.1 检查记录默认值兜底

```sql
DELIMITER $$

CREATE TRIGGER trg_health_record_before_insert
BEFORE INSERT ON wx_health_records
FOR EACH ROW
BEGIN
  IF NEW.status IS NULL OR NEW.status = '' THEN
    SET NEW.status = '已记录';
  END IF;
END $$

DELIMITER ;
```

### 5.4.2 提醒完成时间维护

```sql
DELIMITER $$

CREATE TRIGGER trg_reminder_before_update
BEFORE UPDATE ON wx_reminders
FOR EACH ROW
BEGIN
  IF NEW.done = 1 AND OLD.done = 0 THEN
    SET NEW.completed_at = COALESCE(NEW.completed_at, NOW());
  END IF;
  IF NEW.done = 0 THEN
    SET NEW.completed_at = NULL;
  END IF;
END $$

DELIMITER ;
```

### 5.4.3 反馈内容非空校验

```sql
DELIMITER $$

CREATE TRIGGER trg_feedback_before_insert
BEFORE INSERT ON wx_feedback
FOR EACH ROW
BEGIN
  IF NEW.content IS NULL OR TRIM(NEW.content) = '' THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '反馈内容不能为空';
  END IF;
END $$

DELIMITER ;
```

**设计意图**：触发器主要用于**兜底约束**——默认状态补齐、完成时间维护、反馈内容非空校验。应用层已经做了输入校验，数据库触发器作为最后一道一致性保护，避免异常链路写入脏数据。

# 7 总结

本次数据库课程设计围绕**云端智诊女性健康管理小程序**完成了从需求分析、概念结构设计、逻辑结构设计、物理结构设计到数据库实施与系统测试的完整过程。

**需求与建模**：首先根据小程序的真实业务功能梳理出用户登录、检查记录、复查提醒、问题整理、健康知识和意见反馈六条核心业务线，再把业务对象抽象为 8 个数据库实体。通过 E-R 图和 EER 图可以看出，`wx_users` 是系统的核心，其他 5 类业务数据均通过 `user_id` 与之建立 1:N 关系，并使用 `ON DELETE CASCADE` 保证数据归属和删除一致性。

**逻辑与边界**：在逻辑结构设计阶段，重点考虑了健康管理类小程序的数据边界——系统只保存用户主动录入的健康检查摘要、提醒建议和就诊前问题，**不保存**诊断结论、治疗方案或问诊内容，这既符合小程序审核定位（提审类目：工具/健康管理），也能降低不必要的数据合规风险。所有表均满足 3NF，没有刻意反范式化。

**物理与索引**：物理结构阶段，所有表统一使用 **InnoDB** 和 **utf8mb4** 字符集，主键、外键、唯一索引和组合索引围绕实际查询路径设计。首页需要快速读取最近记录和最近待办，因此检查记录表按 `(user_id, record_date)` 建立索引，提醒表按 `(user_id, done, remind_date)` 建立索引；`openid` 唯一索引保证同一微信用户不会被重复创建。

**实施与对象**：数据库实施部分补充了 2 个视图、2 个存储过程和 3 个触发器。视图 `v_user_health_overview` 聚合首页摘要，视图 `v_pending_reminders` 集中查询未完成提醒；存储过程 `p_create_health_record` 封装事务写入，`p_complete_reminder` 统一完成时间维护；触发器 `trg_health_record_before_insert`、`trg_reminder_before_update`、`trg_feedback_before_insert` 兜底默认状态、完成时间和反馈非空校验。应用层虽然已经在服务层完成了大部分校验，但数据库层约束能够作为最后防线，提高系统稳定性。

**测试与覆盖**：通过 30 个测试用例覆盖登录、记录 CRUD、提醒管理、问题整理、知识浏览和意见反馈六类场景。结果表明每条 API 都能与数据库表结构对应起来，系统具备较好的完整性和可维护性。

**收获与展望**：通过本次课程设计，我对数据库设计的理解不再停留在单纯建表层面，而是更加理解了需求、实体、关系、索引、事务和应用接口之间的联系——一个可用的数据库方案既要能存下数据，也要能支撑页面查询、权限隔离、异常处理和后续扩展。后续如果继续完善该项目，可以考虑：

- 给 `wx_user_questions` 增加 `template_id` 外键，记录问题来源模板；
- 引入 `wx_reminder_logs` 记录订阅消息发送日志；
- 增加数据备份策略（`mysqldump` + 定时任务）与后台内容管理功能；
- 接入全文索引提升 `wx_articles.content` 检索能力；
- 引入读写分离和连接池动态扩容，应对用户量增长。

让数据库从演示型设计进一步升级为可长期运行的产品级设计。
